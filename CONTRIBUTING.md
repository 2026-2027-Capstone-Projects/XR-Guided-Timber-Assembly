## Branches and Commits
Main will contain all the up-to-date approved changes, and it is recommended to pull the repo from there unless you are adding to on-going work. For developing on on-going work, the branches will be named in accordance with the module or issues that they are addressing. Changes from these branches may be merged into main during the development process, however unapproved commits will remain in their original branch into a team member has approved them. Commit messages must be as detailed as possible, covering what work was done, and how it has addressed the requirements set out for that module. Any requirements not yet met must also be noted in the commit.

## Pull Requests
All code pull requests (anything that is not exclusively docs-related) must be approved by a team member that is not the contributor. This rule is intended to ensure code quality, and prevent issues/conflicts with pre-existing code or the project requirements. Unless discussed and agreed upon otherwise by the team, all pull requests will only require one teammate's approval in order to be merged with main (assuming the branch passes all required tests). This teammate must be another developer assigned to the issue or module your commit is addressing, or a developer that has familiarized themselves with the issue when there is not another teammate assigned to your issue.

## Where It Lives
For any files that are not code-related (ie. docs), there exists designated folders for these. Any files or file edits that will not impact code may be pushed to Main without a pull request or approval from another team member. For example, changes to the README will not require a teammate to submit and await approval on a pull request. These changes may be pushed straight to Main or the desired branch.
